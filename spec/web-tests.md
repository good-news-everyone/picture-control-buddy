# Reference tests of the browser version

Part of the pipeline lives in two copies: Python (training, fitting, reference) and the browser (Rust -> WebAssembly, GLSL shaders). Python is the source of truth. The browser copy is checked against fixtures made by the current Python code, so after retraining the model the fixtures are rebuilt, and the tests show whether the browser has caught up.

## How to run

```
node web/test.mjs          # from the project root, exit code non-zero on failure
```

- Levels 1 and 1a (RAW decoding) run in Node, levels 2 and 2a (shaders) run on the `web/test.html` page in headless Firefox via puppeteer-core (verified: Firefox uses the GPU, not software rendering).
- Required: node, Firefox (the path can be overridden with the `FIREFOX` variable), `npm install` dependencies in `web/` (installs puppeteer-core). After changing the Rust code: `sh web/build.sh`, then the test.
- The `web/test.html` page runs the manifest frames and returns the metrics in `window.__result`; there is no interface, no need to open it manually. The visual stand is separate, `web/bench.html`.

## When to rebuild what

- A reference Python module changed (rawdev, devpairs, render, devmodel, vignette, profile_model): `python3 web/make_golden.py` -> `node web/test.mjs`. A red test after the rebuild means the browser copy must be brought up to date.
- A target-decoding reference changed (pairs, match edit metadata, wbmap): `python3 web/make_target_golden.py` -> `node web/test.mjs` (levels 1b/1c).
- Only the browser code changed (raw/src, lib/*.js, test.html): just `node web/test.mjs`; the fixtures are not touched. A green test means the browser has not fallen behind.
- A tolerance in `web/golden/manifest.json` is relaxed only with a recorded reason here (as for NEF in item 1). Tolerances are edited in `web/make_golden.py` (the TOL dict), not in the manifest by hand.

## How it is organized

- `web/make_golden.py` — builds the fixtures from the Python code into `web/golden/`: `manifest.json` (what to check, tolerances) and binary files.
- `web/test.mjs` — one command: runs both parts, prints metrics with tolerances, exit code non-zero on failure.
- `web/test.html` — the executor of the shader parts: reads the manifest, runs synthetic and frames, metrics into `window.__result`.
- Timing (decoding, shader) is printed in the stand, not checked in tests.

Level 1d: `web/lib/resample.js` is an exact port of Pillow 13's kernels, not an approximation (canvas/createImageBitmap scaling is forbidden, spec/web-schemas.md §6.2). Reverse-engineered conventions (from `src/libImaging/Resample.c` / `Geometry.c`): resize is a separable convolution with center-aligned samples (`center = (xx + 0.5) * scale`), the kernel support widened by `max(1, scale)` when downsampling, weights normalized by their sum, and the horizontal pass runs first unless the image shrinks vertically more than twice as much as horizontally. F-mode (float) resamples accumulate in float64 and store float32 unclamped; 8-bit images quantize each pass's weights to int32 with 22 precision bits and keep an 8-bit intermediate — the port reproduces this bit-exactly. `Image.transform`/`Image.rotate` are point-sampled inverse maps (output pixel center `(x + 0.5, y + 0.5)` mapped to the source, then `−0.5` into pixel-index space; 2×2 bilinear / 4×4 Catmull-Rom bicubic with clamped columns and duplicated edge rows) with **no antialiasing**, and a mapped center outside the source fills 0. `devpairs.radial` is numpy, not PIL: bilinear with u/v clamped to `[0, w − 1.001]`; because the pipeline's `(s, k)` come from `np.arange`, the whole computation promotes to float64 and the port computes in float64. **8-bit warning:** `pairs.py`/`devpairs.py` resample the *target* and the embedded JPEG in 8 bit (PIL RGB) — LANCZOS/BILINEAR with int32-quantized weights and an 8-bit output — so the aligned `y` is quantized to 1/255 steps; only the linear `x` path is float. A float-only port of the target resize can be off by up to ~0.5 level; the level-1d u8 cases pin the integer path exactly.

The reference is not the full-resolution build but `build_dbg` **replayed on the shipped inputs** (`pair/<key>.in.json`): the level-1 linear fixture (the browser decoder's own output — no full-res dump), the embedded JPEG capped at 768 px and the working-size target (the target path is 8-bit, so `y` stays exact). This decouples the port's exactness (x/y within 1–2 ulp of the replay) from the honest equivalence gap of the ≤1600 px inputs, which `in.json` `vsBuild` records per pair (x ≤ 0.039, ncc ≤ 0.039) and the test guards. Two decoder conventions are undone at the boundary, not inside the port: the frame rotation (the browser decoder rotates by the EXIF tag like `render.linear`; `preparePair` takes `unrotate` = `(4 − render.TURNS[orientation]) % 4` CCW rot90 steps back to the sensor frame of `rawdev.develop`, which `devpairs.oriented` works on) and the MX/MY margins (already cropped by the decoder, like `rawdev.develop()[MY:-MY, MX:-MX]`). `np.linalg.solve` on the vignette normal systems is a direct Gaussian solve (the `1e-3`/`1e-6` ridges keep them well-conditioned). Level 6: 512^2 cutouts (2 for each of the 5 set frames: center and a quarter of the frame) from the `render.py` neutral, the input is shared with the browser — a PNG that both sides decode. Controls (stored in golden as `.NP3`): all zero (identity), Sharpening 9/-3, Mid-range 5, Clarity 2/-2, mixed triples at scales 2 and 4 — 80 cases. Comparison in 8-bit levels: mean ≤ 0.5 (the main criterion from the fixture), max ≤ 8 is a safety net against gross errors. Actual: mean ≤ 0.32 (half ≈ 0.25 is the fixture PNG rounding), max ≤ 1.23.

The browser Gaussian is not the truncated discrete Gaussian: Python does FFT with reflect edges, and for subpixel sigma (sharpening) the FFT filter is substantially wider than the discrete kernel. `web/lib/detail.js` builds the kernel by a direct Fourier sum of the same frequency response `exp(-2(pi*sigma*k/N)^2)` with the numpy pad window N and convolves separably with reflect edges (one kernel for CPU and WebGL2). The GPU matches the CPU path bit-exactly; CPU vs FFT-Python — mean ≤ 0.02 level.

Level 9: measured 2026-11-19 (Node 22, this machine). **Single-pair** (`dsc_6550` alone): browser fit cost 11.78, 13/30 iterations, ~7.5 s; every group is *better* than the Python reference, the worst group margin **−2.93 dE** (all-mean 2.17 vs Python 5.55 — the shipped reference is the two-pair Python control, which the single-pair fit beats everywhere on its own frame). **Two-pair** (`dsc_6550` + `skl_3024`): cost 136.51 (Python 139.37 — different random realization, not comparable directly), 30/30 iterations — both fits run to the noise-floor cap, ~31 s ≈ the Python-side 31.8 s baseline; frame-wide the browser result is better (all-mean 5.24 vs 5.55, per-pair test-sample scores 5.27/6.78 vs Python 5.57/6.50), but the 40-pixel **skin** group (0.09% of the reportMask pixels) lands +0.68 dE over Python — above the 0.1 dE bar. The bar is therefore asserted on the single-pair case (the task minimum); the two-pair table is printed and recorded here instead of relaxing the tolerance. Why the skin gap is cross-sample variance, not a port error: applying Python's *own* two-pair control to the same prepared inputs through the browser CPU path reproduces the shipped per-group regionSums to ≤ 0.001 dE (so prediction/labels/masks are exact); across mulberry seeds the skin margin scatters +0.33…+0.68 dE while the other groups stay within ±0.4 dE — each fit optimizes its own random sample, and Python's shipped sample is one realization the browser cannot and should not reproduce (spec/web-schemas.md §6.4). ## Known anomaly: DSC_6203, x1.040 between LibRaw and rawler

`renders/check/DSC_6203.NEF` is decoded 4.0% darker by LibRaw (dcraw_emu, the reference) than by rawler (web/raw.wasm), purely multiplicatively on all channels, without a black shift. As if LibRaw's normalization denominator is 16004 instead of 15375 = 16383 - 1008. The other project NEFs (including the overexposed sunset DSC_6132) match within the item 1 tolerance, the DNGs almost exactly. The hypothesis about LibRaw's adaptive white reduction on a large overexposure **was not confirmed**: DSC_6203 has no clipped pixels in either output, and DSC_6132 has clipping yet matches well. The TIFF/Nikon tags of adjacent frames do not differ. The cause is not found; the frame was excluded from the reference set, the file stays in the project for analysis. The lib.rs note "rawler gives 15892" is about a different effect (the white level from the camera catalog) and is not relevant here.

## Resolved anomaly: compare-mode mapping at 1280×800

The level-8 assertion "compare modes share the same zoom/pan mapping" was reported to
fail at a 1280×800 window and pass at 800×600. Investigation (2026-11-19) found the
mode math itself exact at every size — the per-mode viewports in
`web/lib/compare-view.js` (`viewportAt`/`mapPoint`/`place`) all derive from one shared
`view` state and provably agree for any canvas size — and the failure reduced to the
canvas backing store drifting from the element's CSS box: it was sized from the
truncated integer `clientWidth/clientHeight` while a fractional box (e.g. 655.15 px
high at 1280×800; integer at 800×600) stretched the bitmap and skewed the mapping,
and any window resize landing between the per-mode captures changed `base()` under
the assertion. The fix: `sizeCanvas()` sizes the backing store as the rounded
fractional box, one place that owns the canvas coordinate space; the mode math was
not changed. The mapping and the zoom/pan assertions now run at **both** 800×600 and
1280×800 in level 8 (`viewAssertions(tag)` in `web/test.mjs`, the second pass after a
`page.setViewport` resize — the BiDi way to size the headless Firefox window, the
`-width/-height` launch args are ignored — with a geometry-settle wait so the captures
never straddle a pending resize).
